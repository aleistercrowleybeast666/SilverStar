# LOGFILE v1 firmware development evidence — 2026-10-13

This is software development evidence for the new read-only TF log service. It is **not completed critical-contract, stack, original Power of Ten, hardware or flight acceptance**. No TF card, serial port, programmer or actuator was operated. Navigation and deployment logic were not changed.

The original baseline had no LOGFILE service. The development failures below are not claimed to be defects reproduced in a released file-service implementation. The cancellation interleavings and close-error cases have post-fix fault regressions; no pre-fix failing executable for those races was retained. Inspection of the earliest saved generated sources (`lf13f4`, then `lf13b4`) confirms they already contain the atomic cancellation/publication and close-error latch fixes. A preceding implementation cannot be reconstructed from those saved sources without inventing a historical mutation. **The missing pre-fix race/close-failure reproduction is itself a safety-batch/manual-acceptance blocker**, independently of the stack and hardware gaps; this batch does not satisfy the complete pre/post evidence requirement.

## Source and contract boundary

`owned_files.json`, `source_snapshot.sha256.json`, `source_snapshot/` and `tracked_source.patch` identify the exact dirty source snapshot, including previously untracked new files. `environment.json` records the collection time, Git HEAD, working-tree status and tool versions. That HEAD alone is not the implementation identity. Each run has the saved project/configuration, generated ownership/source graph, hashes of generated inputs, artifact hashes, and complete command output. The `.elf`, `.bin` and `.hex` themselves remain in their distinct `.work` build directories; hashes prevent attributing a different binary to this run.

Shared contracts are `contracts/log_file_service_v1.json`, `contracts/session_export_v1.schema.json` and its golden manifest. Protocol commits were `cb944b7` and `14f8e1b`. SSLOG container 0.0, embedded Descriptor and external `.ssdecoder` 1.2 are unchanged. The new file service version is 1, export schema version is 1, and the development product version is 0.1.3. The golden payload `123456789` is synthetic bytes, not a valid SSLOG file.

The service uses the existing Console maintenance line interface. SerialTask parses and polls a single bounded mailbox; LoggerTask alone accesses FatFs. LIST/META/READ expose older numbered missions in PREFLIGHT, READY and POSTFLIGHT while current preflight recording continues. The current mission is excluded even while its writer is temporarily closed. FLIGHT and other unapproved lifecycle states reject work. Metadata hashes advance at most 512 bytes per iteration; READ responses contain at most 64 bytes with CRC32. The whole-file token is a size/CRC change detector, not strong identity or authentication.

CAPS reports device and boot IDs as unknown. Clients must restart from offset zero after disconnect, timeout, cancellation or reboot; matching prefix/CRC/size does not authorize automatic continuation. DELETE is immediately UNSUPPORTED and has no unlink backend. Source logs are retained on every success and failure path. A private file/directory close failure latches service failure until reboot, preventing reuse of uncertain FatFs objects.

The dedicated suite reports 8 passed. It includes the real C golden READ response, normal enumeration/hash/read/EOF, malformed path/token/integer input, current-mission and flight locks, busy requests, stale size/cache, cancellation during I/O and immediately before publication, submission during timeout cleanup, continued polling beyond 30 seconds total, read failures and close-failure latching. F1 and F4 adapter payloads are byte-identical; four logging/maintenance source combinations and missing-storage rejection are checked. Host mocks are explicitly not a TF-card or MCU test.

`CommonFormat_Print` return values are explicitly discarded at the new fixed-format sites because the response capacity is checked to be at least 512 before dispatch, internal result arrays are exactly 512, and all rendered fields have fixed bounds. Including maximum uint32 decimal fields, six-digit file IDs, the 19-character token and 128 hex data characters, conservative output lengths excluding NUL are CAPS 133, PENDING 45, ERR 59, META 150, READ 255 and LIST 106 bytes. The existing formatter bounds each write and NUL-terminates even a truncated buffer. For these fixed inputs truncation is unreachable under the reviewed bounds; invalid small caller buffers are cleared and rejected before formatting. A future field/capacity change must redo this reasoning or check the returned required length before publishing. This local return-value justification does not establish completed critical-contract acceptance or certify the formatter's whole-program stack behavior.

`results.json` records individual exit codes and complete final scope. A final full-Host result must be read from its own complete log, not assembled from earlier runs. Four optional-maintenance regression skips are expected scope cases and are listed in the pytest output.

## Memory and unresolved acceptance

The final F407 memory report is main SRAM **102388/131072**, CCM **59400/65536**, FLASH **337848/524288**, with no heap symbols. Main SRAM is only 12 bytes below the **unchanged 102400-byte project threshold**. Neither physical spare bytes nor this threshold prove task stack safety. The new mailbox, worker buffers and private FatFs FIL/DIR objects use `PLATFORM_CPU_FAST_BSS`. The F407 and F1 Flight diskio implementations always DMA through their existing `s_sd_scratch` sector and copy with CPU `memcpy`; these private file-service objects are not DMA targets. The DMA scratch objects and thresholds were not changed.

The emitted `stack-report` fails closed with:

```text
ValueError: Changed or unknown complete callback binding source: System/Src/system_log_file.c
```

The checker stops at its first unknown full-source identity. It has **not** accepted the new service/adapter/header inputs, the changed Console and LoggerTask callers, or the complete compiler dependency graph for those paths. Its hash tables, callback restrictions and thresholds were not relaxed. Compiler `.su` frames for the changed functions are saved only as local-frame evidence; they are not a complete call-path bound.

Before stack acceptance, manually review and bind the exact source/header/dependency identities and actual linked call sites for SerialTask → Console → parser/poll/formatting and LoggerTask → file worker → FatFs → diskio/HAL. That work must include cancellation/critical sections, standard/library callees, HAL callbacks, the existing FreeRTOS task entry exceptions, interrupt nesting, dynamic/indirect frames and main/MSP. Then rerun the unchanged strict checker against a fresh matching ELF. Linked third-party ownership remains visible in the generated source graph: STM32 HAL/CMSIS, FreeRTOS 11.3.0, FatFs and the selected SX1280 library; no first-party text-gate result certifies those libraries.
