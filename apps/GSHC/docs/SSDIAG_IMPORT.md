# 工程 ssdiag 导入与 SWD 调试

SCG 的每个目标工程根目录提供固定入口：飞控为 `Flight.ssdiag`，地面站为 `Ground.ssdiag`（Ground 拼写正确）。它们是纯数据，不内嵌 ELF，也不会在 GSHC 中执行脚本。旧 R04 的 `SilverStar.ssdiag` 格式及原文件名继续兼容，不需要改名、移动或覆盖现有 R04 文件。

## 正常流程

1. 在 SCG 生成相应目标。首次没有 ELF 时，根描述明确标记 `pending_build`；没有伪造哈希或符号地址。
2. 使用 SCG 构建入口。SCG Host 先将根描述标记为待编译，正常构建成功后读取 Make 报告的实际 ELF 输出，再更新相对路径、SHA-256、目标及诊断字段绑定。失败或取消不发布旧成功状态；缺少诊断依赖或有效 ELF 时明确报告不可用。目标 Make 只编译、链接和报告产物，不执行诊断绑定工具。
3. GSHC 第四页只有“SWD 调试”和“串口”两个子页。地面站串口、飞控维护串口和 SWD 探针的选择/连接/断开在上边栏；SWD 仍只在启动时枚举一次，随后由用户手动刷新，不会自动连接或重复操作。
4. 在“SWD 调试”点“导入 ssdiag…”，选择目标工程根描述。只有唯一成功输出时才自动定位 ELF。每次真实目标连接仍须校验目标型号与 Flash 内容，成功前变量及符号读取保持禁用。导入成功不等于目标已经匹配，不代表 READY/START 或实板验证。
5. “命令输入”与 TF 导出入口在“串口”子页，使用独立维护串口。类别、实例、命令及参数组合出完整命令，也可编辑完整单行；未核实命令会先确认，任务控制和删除仍由专门流程限制。手工 TF 命令只输出响应，手工 READ 不隐式 ENTER、不写本地文件。导出对话框的列表和下载操作先确认维护模式副作用，只有下载事务写本地文件并校验；源日志保留。
6. 默认导出目录可显式设置；临时选取目录仅在完整下载和校验成功后记忆。失败、取消及只读列表不会覆盖上次成功目录。命令、状态轮询和下载共用单个串口所有者，传输期间暂停轮询；关闭失败保留所有者，需重试释放。

## Debug / Release、移动与重定位

- 整个工程移动后，根描述按新位置解析相对路径，不依赖旧机器绝对路径。
- Flight 的 `CONFIG=Debug all` 和 `CONFIG=Release all` 分别记录输出；存在多个有效输出时，不按文件时间或顺序猜测。仅在缺失 ELF 或存在多个成功输出等明确错误状态显示“选择 / 重定位 ELF…”入口。
- Debug / Release 必须由 SCG Host 根据本次构建的实际输出回执分别绑定；不会猜测 Release 路径覆盖 Debug。存在多个有效输出时，不按文件时间或目录顺序猜测，需明确选择对应 ELF。
- ELF 缺失、内容过期、目标/绑定不匹配或未知字段会导入失败并清除旧符号状态；不能继续使用之前成功导入的地址。真实 Flash 不匹配时，同样禁用变量并停止符号 RAM 读取。
- 高级 ELF 筛选保留，能力有限：裸 ELF 不能可靠推断确切 MCU 型号；只有配套描述或当前会话已由描述证明的精确哈希才可用，不会从 Cortex 内核猜测型号。

## 构建工具与边界

绑定实现保留在 SCG Host 的 `silverstar_diagnostics` 中，不复制到目标工程的 `Generated/`，也不进入固件源图。使用现有 Python 和 pyelftools **0.33**；需要时配置 `SILVERSTAR_ELFTOOLS_PATH` 指向既有环境，不自动安装或下载依赖。缺少依赖时报告不可用，不伪造成功绑定；静态分析构建不替换运行固件身份。

生成工程的正常 `all` 目标仅输出实际 ELF 路径回执。单独运行 Make/EIDE、编译单个 `.o` 或其他质量目标，不会自动发布根 ssdiag 绑定；请回到 SCG 构建入口完成一次正常构建（可以是增量构建）。自定义构建编排也应在可信 Host 中先标记待构建，仅在成功构建后按明确的实际输出调用共享绑定接口，不得从导入的描述文件加载或执行代码。

新工程描述契约由 `contracts/swd_project_descriptor_v1.json` 管理；嵌套的既有诊断绑定与旧 R04 描述仍按 `swd_diagnostics_v1.json` 和既有导入器验证。哈希只证明文件一致，不能代替 live Flash 校验或硬件安全证明。软件回归使用假后端及离屏 Qt，不建立实探针、实串口、真实触屏或原生 OpenGL 证据。

根 ssdiag 可声明同目录 `SilverStar.ssproject` 和实际选中的维护组件、包版本、profile；它们仍是两个独立文件，描述格式版本保持 1。旧文件缺少声明时明确显示协议未声明。维护协议、文件服务和描述格式版本分别处理：设备的 `SYSTEM DIAG` 能力响应用于确认维护版本和兼容版本，LOGFILE CAPS 单独确认文件服务。旧查询有响应不证明设备恰为 0.0，也不证明 0.1 不受支持；未确认的版本保持待确认。
