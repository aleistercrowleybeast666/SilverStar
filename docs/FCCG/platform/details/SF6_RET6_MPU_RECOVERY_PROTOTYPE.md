# RET6 compact MPU same-instance recovery prototype

Recorded 2026-10-06 UTC. Implementation and final tests: `018ff76bdb5701541ae7545556a4318bf2203107`, isolated `codex/sf6-compact-ret6`, previous checkpoint `0a58c4e25909f2e1af5acf641a8b0aec9e507074`. This is a review checkpoint, **not accepted firmware**. Stable, F407 ordinary behavior, GUI, GSHC and FLP were not edited. No serial/probe/hardware action, flashing, merge or push occurred.

## Scope and behavior

Only compact MPU6050 gains this retry implementation. The generated facade exposes an optional prepared-context query; other devices return UNSUPPORTED for that optional query and keep their existing business operations. MPU's ordinary branch retains its initial probe failure and terminal configuration-fault behavior. Shared adapter preparation was separated from physical initialization without changing ordinary Init's probe/reset sequence. The generated project remains MPU6050 + E28/SX1281 + BMP280, no GNSS, SF6, maintenance off, local SSLOG, CM3 Thumb softfloat STM32F103xE. No queue, logger, algorithm, RAM-cut, NRF or BMP/E28 recovery policy change was made.

A prepared context has valid transport/profile/mount ownership but is not physically initialized. Initial probe/reset failure is returned and remains in the historical startup report. Startup may record a delegated reading-start intent for that prepared instance despite the failed Init; it does not change Init to OK. The selector processes the prepared instance until a readback-verified profile and a real fresh sample exist. Its initialized flag follows actual instance health. Owner activation reaches the same prepared instance even after a startup failure.

Retry uses WAIT_DUE -> BEGIN -> the existing per-register asynchronous configuration/readback and first-sample verification -> physical data, or backoff. Each Process returns after one bounded step. Failed attempts back off 1, 2, 4, 8, 16, then 32 seconds, with a saturating exponent and no total-attempt counter. A 2-second per-attempt elapsed-time limit supplements the existing driver bounds. Millisecond subtraction is wrap-safe for these short intervals. DeviceTask's existing 1 ms `vTaskDelay` remains. ConfigApply delegates instead of executing its old blocking 2500-iteration loop; ConfigVerify retains the existing bounded whole-profile readback once physical READY is reached. Therefore the observed three-I/O recovery Process bound is not a bound on every public API or every startup tick.

FAULT, READY read error and stale/time-inverted sample revoke the old sample, profile validity and initialized/online/healthy state before waiting. Retries never call global SystemImu_Init or memset the instance/selector; sample sequence, source identity, mount, owner and stored generations are retained. Successful BEGIN creates a new configuration generation and the first real sample carries HISTORY_RESET. Stop cancels the reading intent. START's existing source-lock API remains locked to the same instance while physical retries continue; it is not an authorization to START with stale data.

**Qualification is deliberately sticky and conservative.** Any revocation latches qualification_revoked. A later physical sample may be initialized/online and readable, but the public health interface keeps healthy=0. This prototype has no qualification-clear path, no automatic calibration/alignment/origin/arming, and no independent current-ready override. Historical CompletedStartupReport is not rewritten. Thus it does **not** yet deliver the requested pre-START readmission after all prerequisites recover; after START, physical recovery alone cannot restore public healthy/READY. Implementing reviewed current qualification is a remaining product gap, not a passing recovery result.

## Remaining blockers

This checkpoint is intentionally incomplete: pre-START current qualification/readmission is absent; source-lock/epoch and health behavior across the whole flight state machine is not accepted; critical-contract/corrupt-state review, full stack/MSP/ISR closure and F1 IRQ/timebase timing remain unproven. Configuration-generation UINT32_MAX is fail-closed into NOT_READY/backoff rather than wrapping/reusing an epoch; actual new probe/reset attempts stop at that exhaustion, so literal unlimited physical attempts at exhausted epochs are not claimed. That branch is reviewed source, not a focused fault-injection pass. No real RET6 board evidence exists. BMP/E28 existing recovery boundaries were retained; E28's90 ms HALDelay does not become a whole-system yield proof.

Power10 FAIL, stack FAIL, official Host FAIL and the missing 20% RAM margin block complete acceptance. Parent review is required before any later qualification or architecture work; this branch remains unmerged and unpushed.
